CrossDrop — Product & Engineering Direction
Mission

Turn CrossDrop from a powerful remote kiosk/browser-control project into a local-first system for sending, displaying, syncing, and controlling web content across computers and physical displays.

Do not turn it into a generic file-sharing app.

The core differentiator is:

A browser/display is a programmable endpoint.

The user experience should eventually feel as simple as AirDrop/tab-sharing:

Send this → Living Room TV

while retaining CrossDrop's deeper capabilities:

Open → View → Sync → Control → Automate

Phase 1 — Understand Before Changing Anything

First inspect the entire repository.

Identify and document:

Current architecture.
Agent/server architecture.
Controller architecture.
HTTP API.
Python client.
CLI.
Windows tray application.
Web UI.
Browser/kiosk implementation.
Authentication.
Tailscale/network assumptions.
Target/device model.
Multi-screen implementation.
Screenshot implementation.
Browser input automation.
Media controls.
File handling.
Existing tests.
Existing extension/browser integration, if any.

Do not rewrite existing architecture prematurely.

The existing /v1 API should remain the stable foundation unless there is a compelling reason to change it.

Produce a short architecture document before implementing major changes.

Phase 2 — Define the Product Model

Introduce a simple conceptual model:

Devices

A physical machine running the CrossDrop agent.

Examples:

Living Room
Office
Kitchen
Conference Room
Displays

A device can have one or more displays/screens.

Capabilities

Each target should expose capabilities such as:

open URL
screenshot
scroll
click
keyboard/input
media control
fullscreen
display power
file/content display

The UI should hide technical details such as IP addresses and API endpoints.

Users should select:

Living Room TV

not:

100.x.x.x:8080

Phase 3 — Build the Browser Extension First

This is the highest-value first product feature.

Create a Chrome/Edge extension that can:

Send current tab.
Send current URL.
Right-click a page → Send to CrossDrop.
Right-click a link → Send link.
Keyboard shortcut to send current tab.
Select a destination.
Remember a default destination.
Show destination online/offline status.
Show success/failure.
Show recent destinations.

Example UX:

CrossDrop
───────────────
Send this tab to

🟢 Living Room
🟢 Office
⚫ Kitchen

───────────────
Mirror this tab
Send screenshot
Send link


The first implementation should simply call the existing CrossDrop navigation API.

Do not build a new transport protocol unless necessary.

Phase 4 — Make Discovery and Pairing Easy

Current technical/network requirements should eventually be invisible to normal users.

Add local discovery where appropriate, preferably using standard LAN mechanisms such as mDNS/Bonjour.

Desired flow:

Install CrossDrop receiver.
Receiver advertises itself.
Browser extension discovers it.
User sees a friendly device name.
User pairs with a short code or QR code.
Device becomes trusted.
Future sends require one click.

Support private-network deployments.

Keep existing Tailscale support where useful; do not remove it.

The architecture should allow both:

simple LAN pairing
secure/private remote networking
Phase 5 — Implement “Send → View → Control”

Once basic sending works, expose CrossDrop's existing power progressively.

Send

Send:

URL
page
link
image
PDF
file
text
screenshot
View

Allow the sender to request:

current screenshot
current URL
current page state
online/offline state
Control

Expose existing capabilities through an approachable UI:

click
scroll
type
keyboard
play/pause
volume
seek
fullscreen

Do not present all controls immediately.

The user journey should be:

Send → optionally View → optionally Control.

Phase 6 — Add “Mirror / Follow”

This is an important differentiator.

Add:

Mirror this tab

The remote browser follows the local browser.

At minimum investigate synchronization of:

URL/navigation
page changes
scroll position
media playback

Do not initially attempt pixel-perfect screen mirroring.

The goal is:

“This browser tab is now also represented on that display.”

Allow the user to stop following and leave the remote display independent.

Phase 7 — Build Display Groups / Rooms

Introduce groups such as:

Living Room
Office
Conference Room
All Screens

Allow:

Send to Living Room

or:

Send to All Screens

Support multiple displays per device.

This should build on CrossDrop's existing multi-screen capabilities rather than replacing them.

Phase 8 — Add Automation

Once the device/display model is stable, expose automation.

Examples:

Open a dashboard every morning.
Return a TV to a default page after inactivity.
Open a presentation on multiple screens.
Start a video when a URL is received.
Display a particular webpage on a schedule.
Switch displays into fullscreen/kiosk mode.
Run commands against multiple displays.

Provide a clean API/CLI for automation.

Example conceptual API:

display.open("living-room", url)
display.screenshot("living-room")
display.scroll("living-room", 500)
display.click("living-room", selector)
display.play("living-room")


The exact API should follow existing CrossDrop conventions rather than blindly copying these names.

Phase 9 — Smart Content Handling

When content is sent, make the destination behave intelligently.

Examples:

YouTube/video → open and optionally play.
PDF → appropriate viewer/fullscreen.
Image → image viewer.
Presentation → presentation mode when possible.
Normal webpage → kiosk browser.
File → appropriate local viewer.

Do this incrementally.

Do not create a giant content-detection framework before the basic workflow is proven.

Phase 10 — Session Handoff

Eventually support:

Continue this on another device.

Possible flows:

Laptop → TV
TV → Laptop
Laptop → Phone
Phone → Tablet


The conceptual unit should become a browser session/content state, not merely a URL.

Start with URL + basic state.

Do not attempt full browser-session migration initially.

Phase 11 — Developer/API Layer

Treat CrossDrop as infrastructure as well as a UI product.

Maintain:

stable HTTP API
Python client
CLI
automation support

Make it possible for other applications to say:

Open this content on that display.

Eventually provide good documentation and examples.

Product Principles
1. Simplicity at the surface

The normal user should never need to understand:

HTTP
Chromium
kiosk mode
Tailscale
WebRTC
IP addresses
API tokens

They should see:

Living Room TV 🟢

2. Power underneath

Advanced users should still have:

API
CLI
automation
screenshots
browser control
multi-display support
3. Local-first

Prefer:

LAN discovery
direct communication
local execution
no mandatory cloud account

Cloud/relay infrastructure can be optional later.

4. Preserve CrossDrop's strengths

Do not throw away:

kiosk browser
remote navigation
browser automation
screenshots
media controls
multi-display support
API/client architecture

Build the product layer around them.

Competitive Strategy

Do not try to beat:

PairDrop at generic file sharing.
LocalSend at file transfer.
Deskreen at generic screen extension.
VNC/RDP at full desktop remote control.

Instead own the intersection:

Send web content to a programmable remote browser/display.

Borrow UX ideas from:

AirDrop-style sharing
browser tab sharing
casting
second-screen systems
digital signage
kiosk management

But differentiate through programmable browser endpoints.

Development Order

Implement in this order:

Repository/architecture audit
Browser extension
Send current tab
Friendly device/target names
Discovery + pairing
Status/notifications
Send links/files/content
Screenshot/preview
Remote control
Mirror/follow
Rooms/groups/multi-display
Automation
Smart content handling
Session handoff
Developer/API ecosystem

Do not implement everything simultaneously.

First Milestone

The first usable milestone should answer one question:

Can a user install CrossDrop on two machines, open a webpage on Machine A, right-click it, select “Living Room,” and have the page appear on Machine B in roughly one or two clicks?

If that experience is excellent, continue.

If it is not excellent, improve it before adding advanced functionality.

The first version should feel almost magical:

Browse webpage
    ↓
Right-click
    ↓
Send to → Living Room
    ↓
Remote browser opens page


Everything else comes afterward.

Critical Rule for Codex

Inspect and reuse before replacing.

CrossDrop already contains substantial infrastructure.

Prefer:

extending existing APIs
adding adapters
adding a browser extension
improving discovery
improving UX
composing existing capabilities

over:

rewriting the agent
replacing the kiosk architecture
inventing a second API
creating a parallel transport layer

The objective is to turn the existing CrossDrop engine into a polished product, not to start CrossDrop 2 from scratch.
